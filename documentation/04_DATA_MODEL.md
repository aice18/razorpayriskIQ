# Data Model — Sentinel

All data below is synthetic and generated by the project's own generator. No real customer or transaction data is used anywhere.

## 1. Transaction event (Kafka message)

```json
{
  "transaction_id": "txn_00123456",
  "timestamp": "2026-08-30T10:15:00Z",
  "amount": 8700000,
  "currency": "INR",
  "customer_id": "cust_9284",
  "merchant_id": "merch_112",
  "device_id": "dev_5a91",
  "ip_address_hash": "ip_hash_af31",
  "card_fingerprint": "card_fp_9c02",
  "geo_country": "SG",
  "customer_home_country": "IN",
  "label_is_fraud": true,
  "label_ring_id": "ring_007",
  "is_holdout": true
}
```

Notes:
- `label_is_fraud`, `label_ring_id`, `is_holdout` are generator-only fields, stripped before the transaction reaches the scoring/agent pipeline, and only reattached at evaluation time. This is what keeps the held-out evaluation honest.
- IPs and card numbers are never stored raw — always hashed/fingerprinted, even though the data is synthetic, to build the habit and make the "no PII" claim literally true.

## 2. Entity graph

**Nodes:**
| Type | ID field | Example attributes |
|---|---|---|
| Customer | customer_id | signup_date, home_country |
| Device | device_id | first_seen, device_type |
| IP | ip_address_hash | first_seen, country |
| Card | card_fingerprint | first_seen |
| Merchant | merchant_id | category, avg_ticket_size |

**Edges:** created per transaction, e.g. `(customer_id) -[USED]-> (device_id)`, `(customer_id) -[USED]-> (card_fingerprint)`, `(device_id) -[SEEN_ON]-> (ip_address_hash)`, `(customer_id) -[PAID]-> (merchant_id)`.

Ring detection = connected-component / community detection over the Customer-Device-Card-IP subgraph, looking for components with more distinct customers than is plausible for organic shared-device use (e.g., a family sharing one device is 2-4 customers; a ring is 10+).

## 3. Feature schema (per transaction, computed by Flink, stored in Redis)

| Feature | Description |
|---|---|
| `velocity_1m`, `velocity_5m`, `velocity_1h` | Transaction count for this customer/device in rolling windows |
| `amount_zscore_vs_customer` | Deviation from this customer's historical average |
| `amount_zscore_vs_merchant` | Deviation from this merchant's typical ticket size |
| `is_new_device`, `is_new_ip`, `is_new_card` | Boolean first-seen flags |
| `geo_deviation_km` | Distance between customer's home region and transaction origin |
| `entity_degree_device`, `entity_degree_ip`, `entity_degree_card` | Number of distinct customers sharing this device/IP/card in graph |
| `component_size` | Size of the connected component this transaction's entities belong to |

## 4. Ground-truth labeling in the generator

The generator should produce, at minimum, three transaction classes so the held-out set is meaningful:
1. **Normal** — no anomalies, majority of volume.
2. **Velocity fraud** — single actor, rapid/abnormal transaction pattern, no ring.
3. **Ring fraud** — multiple synthetic customer IDs sharing device/IP/card, coordinated timing.

Include a small fraction of **ambiguous/borderline cases** (e.g., a legitimate shared family device, a legitimate travel-related geo deviation) — a system that only ever sees clean-cut cases will report inflated metrics that don't hold up under judge scrutiny.
